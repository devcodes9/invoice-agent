⏺ Here's what I found in the data and the approach I'd take.

  From the data
  - These look like the SROIE dataset: Malaysian receipts in MYR (RM), 6% GST,
    with "Rounding" lines and discount columns. Your validation has to allow for
    rounding and for tax-inclusive prices, or clean receipts will get flagged.
  - X51005268275.jpg and X51005301666.jpg are byte-identical (same md5). Detect
    duplicates and flag them.
  - Resolution ranges from 463px to 1654px wide.

  On your 3 ideas
  1. Free-form agent loop: Skip it. The steps are always the same, so a loop
     only adds randomness. You'd also struggle to defend it under "judgment
     about scope".
  2. Vision LLM → JSON → code validation: Yes, use this as the base.
  3. OCR → LLM: You're right that OCR loses layout, so don't use it as the main
     extractor. It's cheap and useful as a verifier, though.

  Recommended pipeline (fixed, no agent loop)
  1. Extract: a vision LLM returns JSON with a strict schema. Every field can be
     null and carries a legible: true/false flag, and the prompt says "return
     null, never guess". This is the main guard against made-up values.
  2. Ground: run OCR (Tesseract or similar) and check that the extracted total,
     date and amounts actually appear in the OCR text. If a value isn't in the
     text, it's probably made up.
  3. Validate (code): line items sum to subtotal, subtotal + tax + rounding =
     total, tax ≈ 6%, the date parses, currency is MYR.
  4. Agree: do a second extraction at temperature > 0, or with a different
     model, and compare the key fields.
  5. Score: confidence comes from the validation, grounding and agreement
     signals. Don't use the model's self-reported confidence; it's poorly
     calibrated.
  6. Gate: if the image is marked illegible, or too many key fields are null,
     set status UNREADABLE with empty values. Don't take a partial guess.

  What you're missing
  - Sums can pass on made-up numbers. A model that invents values can make them
    add up. That's why the grounding and agreement steps are needed.
  - Calibration proof. Hand-label about 10 receipts (vendor, date, total), then
    show that high-confidence rows are correct and low-confidence rows are the
    real errors. The brief says they'll grade on this.
  - CSV design. Add status (OK / REVIEW / UNREADABLE) and reasons (e.g. "total
    not found in OCR; items≠subtotal"). Line items should go in a second CSV, or
    as JSON in one cell.

  Questions
  1. Which model or API can you use, and is there a cost limit? This decides
     whether step 4 uses the same model twice or two different models.
  2. Is the output CSV only, or do you also want a small review UI? I'd say CSV
     only, given the 2-hour budget.

❯ why are we adding ocr at all, if vision model already reads the image?        

⏺ Because the vision model can't reliably check itself.

  Why a second reader helps
  - When the vision model gets a value wrong, a second pass by the same model
    often makes the same mistake. It will read a smudged 8 as 3 both times, and
    it will make up a clean total on a blurry receipt both times.
  - OCR reads the image in a completely different way (character by character,
    no language guessing), so its mistakes are different. If both readers agree,
    you can trust the value much more.
  - It catches made-up values: if the extracted total 127.20 doesn't appear
    anywhere in the OCR text, flag the row.
  - OCR also scores its own confidence per word. Low scores across the whole
    image are a cheap, deterministic signal that the image is bad.

  Downsides
  - OCR fails on the same bad images, so it adds noisy flags exactly where you
    already expect trouble.
  - Matching numbers needs some tolerance (127.20 vs 127,20 vs RM127.20).
  - It's one more dependency to install.

  Alternative: use a different vision model as the second reader, e.g. Claude +
  Gemini. That gives the same "independent reader" benefit with less plumbing.
  It costs more, though, and two LLMs can still make similar guesses.

  My pick: keep OCR, but only as a cheap check on a few key fields (total, date,
  subtotal), not as a full extractor. If time is short, drop it and rely on
  validation + a second model. Either way, write down the choice in NOTES.md.

⏺ 1. If they disagree

  Don't pick a winner blindly. Handle it this way:

  - Default: keep the vision model's value (it's better at layout), mark the
    field disagree, lower the confidence, and send the row to REVIEW.
  - Tie-break with the sums: if only one candidate makes subtotal + tax + 
    rounding = total work, use that one, and still note in reasons that it was
    auto-resolved.
  - If nothing resolves it: leave it as REVIEW and show both values in the
    reason, e.g. total: llm=127.20 ocr=121.20. The reviewer then fixes it in a
    few seconds.

  Your goal is to tell people when the agent might be wrong, not to always be
  right. A disagreement is exactly the kind of case that should reach a human.

  2. How to know the confidence is trustworthy

  Only by checking it against ground truth.

  - Get labels: these are SROIE receipts, and the public dataset has labels for
    vendor, date and total. Or hand-label about 15 receipts, mixing clean and
    bad images.
  - Group by confidence: HIGH / MEDIUM / LOW. For each group, measure what % of
    rows are actually correct.
  - What "good" looks like:
    - HIGH is about 100% correct. This matters most, because nobody will review
      those rows.
    - Nearly every wrong row lands in MEDIUM or LOW. This is the recall of the
      flags.
    - LOW isn't mostly correct rows; otherwise people get alert fatigue.
  - Put the table in NOTES.md, e.g. "HIGH: 28/28 correct, LOW: 4/6 wrong". That
    is your proof, and it answers the "confidence calibration" item they grade
    on directly.

  Two cautions
  - Use 3 buckets, not decimals like 0.87. A precise-looking number suggests
    accuracy you can't back up with 45 samples.
  - Don't adjust the thresholds on the same receipts you measure on, or the
    result will look better than it really is. If you do adjust them, say so in
    NOTES.md.

❯ Whats the approach from high level (zoomed out) that we are talking about     
  here?                                                                         

⏺ A fixed pipeline, not an agent loop:

  image → extract (vision LLM) → cross-check (OCR or 2nd model) → validate 
  (code) → score → CSV

  - Extract: the vision LLM returns JSON and is allowed to say "null / can't
    read".
  - Cross-check: a second, independent reader confirms the key fields.
  - Validate: code checks the sums, tax, date and currency.
  - Score: HIGH / MEDIUM / LOW, based on how many checks pass.
  - Gate: if the image is too unreadable, output UNREADABLE instead of guessing.
  - Output: a CSV with status + reasons, sorted so the rows needing review come
    first.

  Core idea: the LLM does the reading, and code decides how much to trust it.

⏺ No, only the LLM gives JSON. OCR just gives raw text (plus a confidence per

  No second LLM either. The matching is plain code: check whether the LLM's
  value appears somewhere in the OCR text.

  - Numbers (total, subtotal, tax):
    a. Pull every money-like token out of the OCR text, e.g. 127.20, RM127.20,
       127,20.
    b. Normalize them to numbers.
    c. Check whether the LLM's value is in that set.

    the LLM's date.
  - Vendor: fuzzy-match (e.g. rapidfuzz) against the first few OCR lines.

  right field. For example, 127.20 shows up as both TOTAL and CASH. That's fine,
  because the sum checks catch wrong-field mix-ups.

❯ okay, whats the flow now                                                      

⏺ image
    → dedupe (hash)
    → extract ×2 (two vision LLM calls, same JSON schema)
    → compare (field by field)
    → validate (code)
    → score + gate
    → CSV

  1. Dedupe: hash each image and flag exact duplicates.
  2. Extract ×2: each model returns JSON with fields that can be null plus a
     legible flag; the prompt says "null, never guess".
  3. Compare: fields that match are trusted, and fields that don't are marked
     disagree.
  4. Validate: items sum to subtotal, subtotal + tax + rounding = total, tax is
     about 6%, the date is valid, currency is MYR.
  5. Score:
     - HIGH: both models agree and all checks pass.
     - MEDIUM: a minor disagreement or one soft check fails.
     - LOW: key fields disagree or the sums fail.
     - UNREADABLE: marked illegible, or too many nulls. Values stay empty.
  6. CSV: status, confidence and reasons, sorted with rows needing review first.
  7. Eval: compare against about 15 labeled receipts to show the confidence
     levels hold up.

❯ How would we calculate confidence?                                            

⏺ With simple rules, not a weighted formula. That makes it easy to explain and
  to defend.

  Hard signals (any one of these → LOW)
  - Total, date or vendor disagree between the two models.
  - subtotal + tax + rounding ≠ total.
  - The total is null.

  Soft signals (any one of these → MEDIUM)
  - Line items don't sum to the subtotal.
  - Tax isn't about 6%.
  - A non-key field disagrees (e.g. a line item).
  - A non-key field is null.

  Gate (→ UNREADABLE)
  - Either model sets legible: false, or 2 or more key fields are null.

  Otherwise → HIGH.

  The reasons column lists every signal that fired, so the reviewer knows what
  to check.

  Why rules and not a number like 0.83: with 45 receipts you can't calibrate a
  number, but you can show that each level is accurate by comparing against the
  labeled set.

❯ how are we handling legible flag? how reliable is that?

⏺ It isn't very reliable. It's the model grading itself.

  The problem
  - A model tends to say legible: true and then guess the values, which is the
    exact failure we're trying to catch.
  - Pushing it the other way ("say false if unsure") makes it refuse clean
    receipts.

  How to treat it (the two answers mean different things)
  - If it says legible: false, believe it. Models rarely claim an image is
    unreadable when it isn't, so it's a cheap, trustworthy UNREADABLE signal.
  - If it says true, treat it as no information either way. Don't let it raise
    confidence.

  Signals that catch the case where it wrongly says "legible"
  - The two models disagree. On blurry images, made-up values tend to differ
    between models. This is the strongest signal.
  - Many null fields.
  - The sums fail.
  - Optional: a blur score from code (Laplacian variance). It needs no LLM and
    is fully deterministic.

  Verify it: run the one or two near-illegible receipts and check they land in
  UNREADABLE or LOW. If they come out HIGH, the gate is broken. Show that result
  in the Loom video.

❯ nIs deterministic blur score, a best practice?                                

⏺ Partly. It's common, but in a different setting.

❯ would ocr fail on these cases directly? and won't hallucinate or would it     
  anyways give extraction?                                                      

⏺ OCR fails differently from an LLM.

  OCR on bad images
  - It doesn't make up plausible values. It has no idea what a "total" should
    look like.
  - It fails loudly: garbage characters (12?.2O, l27.Z0), missing words, and low
    confidence scores per word.
  - It can still misread a character with high confidence (8 → 3). That's rarer,
    though, and not systematic.

  LLM on bad images
  - It fails quietly: clean, believable values that may be made up.

  So OCR gives a useful gate signal: the average word confidence across the
  image. If it's low, the image really is hard to read.

  This is much simpler than before
  - No field matching, just one number per image.
  - It's a better "is this readable?" check than the LLM's legible flag or a
    blur score.

  Tradeoff: it brings back the OCR dependency (Tesseract). The threshold also
  needs a quick check on the bad images.

  My pick: optional. Add it only if the near-illegible receipts slip past the
  model-disagreement check in your first test run. Test first, then add.

❯ why extract with same temperature for both calls?                             

⏺ Temperature isn't what makes the two readers independent. Using two different
  models already does that.

  - Temperature 0 on both: each model gives its most likely reading, and results
    stay close to reproducible across runs.
  - Higher temperature: adds random noise. Disagreements would then partly come
    from chance, not from actual uncertainty in the image, which gives false
    flags.
  - When a higher temperature would make sense: if you used the same model
    twice, since two calls at temperature 0 would just give the same answer.

  Temperature 0 isn't perfectly deterministic either, which is why the plan
  caches the LLM outputs.
